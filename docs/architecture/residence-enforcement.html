ADR-0010 defines residence rules: every domain concept — a calculation, a JSON shape, a document’s state, a write path — must have one owning module. The rules existed only as prose, and prose drifts. This package adds the missing enforcement: ① a ratchet script (scripts/residence_check.py) that measures five violation counts against committed baselines and fails any commit that increases one, while automatically tightening the floor whenever debt is retired; and ② ownership manifests (first: procurement) that tell a human or an AI agent which module already owns a concept before they create a duplicate. Verified end-to-end: clean tree exits 0, a planted violation exits 1 with a hint pointing at the owner, a simulated fix auto-tightens the baseline 41 → 39.

01

The problem: rules that can’t be checked, drift

The codebase already legislates placement — which folder a file belongs in — and that is largely followed. The June architecture review found the real gap is residence: which module owns a concept. A rule with no home gets re-implemented at every call site; each copy starts identical and slowly diverges. Because this codebase is AI-co-developed, the effect compounds: agents pattern-match the surrounding code, so every existing copy makes the next copy more likely. A new helper in the correct folder is still scatter.

“If a rule can’t be checked, it’s documentation — and it drifts.” ADR-0010, one week before its own rules drifted

One week after ADR-0010 was adopted with two worked proofs, we measured the un-mechanized rules against the tree:

Drift, measured 08 Jul 2026Rule violatedCount
Ad-hoc workflow_state = writers in api/ + integrations/B3 state is derived, never written ad-hoc39
Files hardcoding "Vendor Selected" instead of importing the shared predicateB2 one owner per data shape8
Frontend files calling raw updateDoc outside the write-safety seamF5 writes through one seam114
Inline JSON.parse of backend shapes inside pages/F2 shapes parsed at one accessor200

None of these can be fixed in one move — a hard “zero violations” gate would block every PR or force a big-bang refactor nobody schedules. The enforcement has to make the status quo legal and regression illegal. That shape has a name: a ratchet.

02

What was built — four artifacts

i

The ratchet script

scripts/residence_check.py

Stdlib-only Python, no bench context, runs from any cwd. Five checks, each mapped to an ADR rule. On failure it prints a route hint — the module the concept lives in — so the violator (human or agent) learns the correct home at the moment of the mistake.

ii

The committed baselines

scripts/residence_baseline.json

The measured floor: 39 / 0 / 8 / 114 / 200. Checked into git — so every time debt is retired and the script tightens a number, the diff of this file is the progress record, visible in every PR.

iii

The ownership manifest

.claude/context/domain/procurement.md

A verified table — concept → owner → nothing else may… — for the worst-scoring domain. Eight rows; every path grep-verified against real code. Two rows are honestly UNASSIGNED: no owner exists yet, so the rule is “don’t pick one ad-hoc — ask.”

iv

The paper trail

docs/adr/0010 §Enforcement + CLAUDE.md ×2

An Enforcement amendment in the ADR (policy, baselines, and one honest correction — see §05), plus one-line pointers in both always-loaded CLAUDE.md files so every future agent session knows to run the check and consult the manifest.

03

How the ratchet works

Each check counts current violations of one rule and compares against its committed baseline. The policy is deliberately asymmetric — counts may only move down:

current > baseline
✗ Fail — exit 1 New violations were introduced. The run names the check, the delta, and prints the route hint pointing at the owning module. The commit should not proceed.
current < baseline
✓ Pass — and tighten Debt was retired. The baseline file is rewritten downward automatically, so the improvement becomes the new floor and can never silently creep back.
current = baseline
✓ Pass — holding Status quo. Legal, by design — old debt is paid down incrementally, not by decree.

v1 wiring is deliberately modest: the script runs by rule (both CLAUDE.md files instruct running it before committing), not by hook. A Claude-Code hook or CI gate comes only after owner sign-off — so while the rules are still Proposed, a false positive can annoy but never block work.

The five checks and their baselines

CheckRuleWhat it countsBaseline
b3_workflow_state_writersB3 Lines assigning workflow_state in api/ + integrations/ — state should come from one deriver (the future Candidate 6) 39
b1_pure_module_purityB1 Live frappe.db / get_all( / get_doc( / sql( calls inside declared PURE_MODULES. Python tokenize strips docstrings first, so documenting the purity rule can’t trip it 0
b2_predicate_literal_scatterB2 Files hardcoding "Vendor Selected" outside the predicate home (services/procurement_approval.py) 8
f5_raw_updatedoc_filesF5 Frontend files calling useFrappeUpdateDoc / updateDoc( instead of going through the write-safety seam (useEditingLock) 114
f2_inline_json_parse_pagesF2 Inline JSON.parse occurrences in frontend/src/pages — backend shapes belong in one typed accessor 200

The set is extendable by design: adding a check is one Check(...) entry in the registry plus an --init re-measure; declaring a new pure module is one line in PURE_MODULES. The intended trajectory is a growing pure-module registry and shrinking baselines.

05

The ownership manifest — “which module owns this?”

The rules say what kind of module owns a concept; they don’t tell an agent which one already does. The manifest closes that gap. Excerpt from the procurement table (8 rows total, every path verified):

ConceptOwnerNothing else may…
Awaiting-approval predicate services/procurement_approval.py hardcode the state literals or re-implement the pending-item check
Loss % / benchmark rule utils/lossPercent.ts + api/send_vendor_quotes.py (FE↔BE parity pair) re-derive the 10% threshold inline
PR/SB workflow_state transitions UNASSIGNED — Candidate 6, the future deriver add a new writer (ratchet-enforced)
order_list child-row shape UNASSIGNED — no single accessor yet add new inline parses
Counts / aggregates over rows the database — GROUP BY / EXISTS, sidebar_counts.py-style tally rows in a Python/JS loop

The UNASSIGNED rows are the honest part: for those concepts an owner genuinely doesn’t exist yet, and the correct behaviour is ask, don’t invent — while the ratchet guarantees the pile at least stops growing. The section ends with a template note so other domains copy the shape as they’re touched: rows must be verified, not aspirational.

Building this surfaced one correction now recorded in the ADR: services/finance.py, previously cited as the B1 pure-module precedent, is actually mixed — pure calculation alongside live frappe.get_all calls. The genuinely pure exemplar is services/procurement_approval.py (baseline-enforced at zero), and finance.py is reclassified as a split candidate. A sign-off package that corrects its own precedent is more credible, not less.

06

How it was created

Recon & measurement

Grep the drift before designing the cure

Every proposed check was measured against the live tree first (39 / 8 / 114 / 200), so the tooling was shaped by real counts — not hypothetical ones. This is also where the finance.py-is-mixed discovery happened.

Two decisions

Auto-tighten · script-only v1

Owner-chosen: baselines tighten automatically on decrease (the git diff becomes the progress record), and v1 runs by rule rather than by hook — no enforcement hard-gate until the rules are ratified.

Parallel build

Two subagents, independently verified

The ratchet script and the procurement manifest were built concurrently by separate agents, then cross-checked in the main session: every manifest path re-verified on disk, the script re-run from scratch. The script agent independently improved the B1 check — stripping docstrings via tokenize so a comment about frappe.db can’t register as a violation.

Policy

compare() — the contract in ~15 lines

The ratchet policy lives in one pure function (Verdict(ok, message, new_baseline)): above-baseline fails, below-baseline passes and tightens, equal holds. No I/O in the policy; the main loop applies rewrites.

Verification

Three scenarios, real transcripts

Clean pass (exit 0) · planted violation (exit 1, correct route hints for both tripped checks) · simulated fix (exit 0, baseline auto-rewritten 41 → 39). The transcripts in §03 are unedited output.

07

What you get from having this

For AI agents

The failure mode this kills is compliant-looking scatter — a new helper in the right folder that duplicates an owned rule. The manifest answers “who owns this?” before code is written; the ratchet catches the miss afterwards and its route hint teaches the correct home at the exact moment of the mistake. Both CLAUDE.md files wire this into every future session.

For code review

“Did this PR make the architecture worse?” becomes a one-command answer instead of a judgment call. Reviewers stop having to remember which of 39 state-writers are grandfathered — the baseline remembers.

For progress

Every retired violation permanently lowers a number in a committed JSON file. Debt paydown is visible in ordinary PR diffs, it can never silently regress, and the trajectory (39 → … → 0, then Candidate 6 assigns the owner) is legible to anyone reading git history.

For sign-off

ADR-0010 now arrives as a working system: ten rules, two shipped proofs (sidebar_counts, self-fetching facets), running enforcement with measured baselines, and one self-correction. Ratifying it ratifies something already true — and unlocks the harder gate (hook / CI) with confidence it won’t misfire.

Deliberately not in v1

No hook or CI gate (post-sign-off), no fixing of the 39/114/200 existing violations (that’s the backlog’s job — Candidate 6 first, since the scattered state writers are also a known correctness bug), no manifests for other domains yet (they’re added as domains are touched, using the procurement template).
