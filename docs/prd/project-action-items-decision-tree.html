Project Action Item — Decision Tree

How the recompute-from-truth reconciler decides, for every Procurement Order, whether a DN_PENDING or DC_PENDING action item should exist — and whether to create, re-open, leave, or resolve the row. Logic is verbatim from predicates.py + reconcile.py.

NO branch → not an action item (short-circuit) YES → continue / pending loop over PO items

Everything else is excluded by construction — so PO ApprovedMerged CancelledInactive never produce an action item (and an existing row auto-resolves).

Stage 1 · Per-PO predicate — should this obligation exist?

DN Pending

action_type = DN_PENDING

“Dispatched, but the delivery has not been fully recorded as a Delivery Note.”

Is the PO Billable?
billing_status == "Non-Billable" → not pending · NULL/blank = Billable
↓ YES
Is status in the live-delivery set?
status ∉ {Dispatched, Partially Dispatched, Partially Delivered, Delivered} → not pending
↓ YES
Is the PO already fully Delivered?
status == "Delivered" → not pending (nothing left to record)
↓ NO (still open)
For any item on the PO: is it real (category != "Additional Charges"), dispatched (is_dispatched == 1), and not fully delivered (received < expected, per the 2.5%/integer tolerance¹)?
↓ YES, at least one such item
→ DN_PENDING exists for this PO
Title “Record Delivery Note — {PO}”. If no item qualifies → not pending.

DC Pending

action_type = DC_PENDING

“A delivery happened, but no Delivery Challan document has been filed.”

Is the PO Billable?
billing_status == "Non-Billable" → not pending · NULL/blank = Billable
↓ YES
Is status in the live-delivery set?
status ∉ {Dispatched, Partially Dispatched, Partially Delivered, Delivered} → not pending
↓ YES
Does a Delivery Challan already exist?
a non-stub type=="Delivery Challan" PDD is parented to the PO → not pending
↓ NO challan yet
For any item on the PO: is it real (category != "Additional Charges") and has it actually been received (received_quantity > 0) — i.e. a Delivery Note exists? (Tested at item level, not via status, so a sticky Partially Dispatched PO with deliveries is not missed.)
↓ YES, at least one received item
→ DC_PENDING exists for this PO
Title “Upload Delivery Challan — {PO}”. If no item is received → not pending.

A single PO can satisfy both predicates at once (e.g. Partially Delivered with no Challan) → it carries one DN_PENDING and one DC_PENDING row, independently.

This whole tree runs per project — on each PO/DN/DC event (enqueued, after-commit) and nightly — so a missed event always self-heals at the next reconcile.

Notes

  • ¹ Tolerance (DN “fully delivered”). Mirrors calculate_order_status: float quantity → delivered iff received ≥ quantity × (1 − 0.025); integer quantity → received ≥ quantity. Matching this guarantees the predicate can never disagree with the PO’s own derived status.
  • Assignee. Every row is created with assigned_role = "Nirmaan Project Manager Profile".
  • Source of truth. services/action_items/predicates.py (Stage 1) and services/action_items/reconcile.py (Stage 0 + Stage 2).
  • Scope. v1 is PO-only; Internal Transfer Memo deliveries and a future DISPATCH_PENDING type are deferred (they slot in as additional action_types on the same tree).
