Bulk Import Outflow

How the matcher decides what a bank transfer paid

You upload a bank statement of money that has already left the account. For each line, the system tries to find the one record in Nirmaan that the line settles. This document explains exactly what it checks, in what order, and why each rule exists — every rule here was written to fix an observed failure on real data.

01What matching is actually for

The import pays what someone has already approved. It never approves anything, and it never creates a payment out of thin air. So matching has exactly one job:

The question the matcher answers

“This ₹18,679 left the bank on 28 July. Which approved record in Nirmaan is it paying?”

There are three places that record could live, and the matcher searches all three:

LedgerWhat it isMatched by
Project Paymentsmoney owed against a PO or service requestbank reference, or vendor + amount + date
Project Expensesproject spend with no PO behind itamount, corroborated by the description
Non Project Expensesoffice and company overheadsamount, corroborated by the description
Only “Approved” is ever matched

A record sitting at Requested or CEO Pending is not in the candidate pool at all. The matcher literally cannot see it, so a transfer against one comes back plainly Unmatched — no status, no nudge, no “approve this first” link. Nothing is ever offered that could not then be settled.

And one rule that shapes everything below:

The matcher proposes. It never decides.

Every function here returns ranked candidates. The outcome is derived separately, and the choice is made by a person. That is not caution for its own sake — it is forced by the data. One bank account in this database maps to three legally distinct D.S. Ductofab companies with different GSTs, and to two separate Siemens entities. There is no signal in a bank statement that separates them.

02The ladder: five steps, in order

Precedence is deliberate. Each step can end the row; later steps only run if the earlier ones stayed silent.

1
Is this row even eligible?

Already imported in an earlier batch, a repeat of a line earlier in the same file, or a transfer the bank marked as failed.

→ Skipped
2
Did somebody already tick this by hand?

A Paid payment already carrying this bank reference. Checked against a deliberately separate pool from the candidates.

→ amounts agree (within ₹1) Skipped   differ by more Mismatched
3
Is there an approved payment?

Pass A — the bank reference matches. Pass B — the vendor, the amount (±₹1) and the date (±3 days) all line up.

→ zero or more candidate groups
4
Is there an approved expense?

Amount within ±₹1, then scored up by anything the description text corroborates.

→ zero or more candidates
5
Count what was found

One candidate is a confident suggestion the screen pre-selects. Several is an ambiguity it presents without guessing between them.

→ ≥1 Matched   none Unmatched
Why steps 1 and 2 come first

Both describe money that must not be recorded again — or at all. A failed transfer still carries a perfectly good bank reference and would match a payment happily. Checking eligibility after matching would mean offering it.

03Step 0 — Making values comparable

Before anything is compared, both sides are converted to a canonical form. Raw string equality fails on real data in every field the matcher depends on.

The split that matters most

Identity forms

normalize_account, normalize_reference

Two values that normalise equal are treated as the same thing. These must never merge things that are genuinely different.

Scoring forms

normalize_name, name_tokens

These feed a ranked suggestion a human confirms, so they are allowed to be lossy. They even singularise words — a heuristic that would be indefensible as an identity rule.

Never cross the streams

A normalised name must never be used as an identity key. And a normalised account — even though it is an identity form — must never be treated as a vendor identity, for the shared-account reason above. An account narrows a candidate set; a person picks from it.

Bank account numbers

Strip whitespace and separators, then strip leading zeros.

Why leading zeros — a real failure
SourceRawNormalised
bank statement0869102000002783869102000002783
vendor master869102000002783869102000002783
vendor master (another record)'50200023578202 '50200023578202

A raw compare misses the first pair entirely and the vendor looks unknown. The trailing-space case is the mirror image of the same problem.

An all-zero value normalises to "0", not the empty string — so a genuinely zero account stays distinguishable from a missing one.

Bank references (UTRs)

Strip all whitespace and upper-case. Leading zeros are preserved — unlike an account number, a reference is an opaque token and its first character is significant.

226 live payments have a padded UTR

Values like ' 504918114686' sit in the ledger today. The pre-existing guard elsewhere in the app strips the incoming value but compares it against unstripped storage, so those rows are invisible to it. Normalising both sides is the fix — which is why this is a function and not a bare .strip() at the call site.

Party names

Case-fold → turn & into the word and → reduce every run of non-alphanumeric characters to one space → collapse whitespace.

The one the canonical string cannot fix

e-Hub becomes e hub while eHub becomes ehub. Those are not equal as strings. That case is resolved at the token level instead — which is exactly why the canonical string and the token set are two separate functions.

Name tokens

Split the normalised name, expand legal abbreviations, then singularise each token.

Abbreviations expanded

pvt→ private
pvtltd→ private
ltd, ltd.→ limited
co→ company
corp→ corporation
inc→ incorporated

So Dhatri Networks Pvt Ltd and Dhatri Networks Private Limited agree.

Singularisation

Drop one trailing s from a token of 4+ characters that does not already end in ss.

solutions→ solution
express→ expressthe ss guard
gas→ gastoo short

Exists for one observed pair: the statement’s Absolute Air Solutions against the master’s Absolute Air Solution.

Noise words

Nine tokens carry no discriminating signal between two Indian trade names and are weighted out during scoring:

and · the · private · limited · company · corporation · incorporated · llp · llc
Why and is noise

The statement writes RIDDHI SIDDHI FASTENERS INDUSTRIAL NEEDS; the master holds RIDDHI SIDDHI FASTENERS & INDUSTRIAL NEEDS. Treating the connective as noise is what lets those two meet.

Why trade words are not noise

enterprise, roadlines, hardware are deliberately absent from the list. They are exactly what separates Sri Sai Enterprises from Sri Sai Roadlines — two different live vendors.

The in-file duplicate check is separate from the cross-batch one for a mundane reason: the cross-batch lookup cannot see the file it is currently reading. Leaving it out is not cosmetic — both copies would offer the same record, and settling both would violate the database’s uniqueness constraint.

05Step 2 — The already-paid guard

People tick payments Paid by hand all day. Half a statement being hand-ticked before it is uploaded is the normal case, not an edge case. So before looking for anything to settle, the matcher asks: is there already a Paid payment carrying this bank reference?

This is a SKIP, not a match — and it is load-bearing

Delete this check and a hand-ticked payment comes back Unmatched, whose obvious next click records the same money a second time.

This is the ONLY route to “Mismatched”

The candidate passes below match on an amount within a rupee, so a genuine disagreement is arithmetically impossible there. If you ever see a Mismatched row, it came from here.

The guard also matches on the bank reference alone — never on the vendor heuristic. A heuristic hit here would skip a row on a guess, which is the one outcome a duplicate guard must never produce.

The middle row above was a live defect, fixed 2026-08-07

This branch originally compared the amounts exactly, while every other amount check in the feature used the ₹1 window. Since the bank rounds to the whole rupee and 31.4% of payments carry paise, every hand-ticked payment with paise on it was reported as a discrepancy — under a note suggesting TDS.

On a real 26-row statement that was 8 rows flagged for investigation, over gaps of 0.14, 0.15, 0.18, 0.40, 0.57, 0.68 and 0.86 — ₹3.12 of “discrepancy” in total. All eight now skip correctly. The lesson generalises: when a tolerance has a list of call sites, the branch not on the list is the one to check.

06Step 3a — Working out who was paid

Pass B of the payment search needs a vendor. Resolving one is its own scored search, and it never returns a single answer — it returns a ranked list.

The two signals

SignalScoreNotes
Bank account and IFSC both match0.95the IFSC separates a genuine hit from a coincidental digit collision
Bank account matches0.8018 vendors share an account with somebody else
Normalised name matches exactly0.75after all the normalisation above
Some name words in common0.60 × containmentdropped below 0.35; needs ≥2 non-noise words to score at all

Containment, not overlap

The share is computed against the smaller of the two token sets:

containment = shared_tokens / min(row_tokens, vendor_tokens)
score       = 0.60 × containment
Why not Jaccard
Statement
Md Arsad Alam
Vendor master
Md Arsad Alam Electrical Work
MeasureCalculationResultVerdict
Jaccard (overlap ÷ union)3 / 50.60punished for the vendor being more specific
Containment (÷ smaller set)3 / 31.00correct — the statement name is a complete subset

A bank statement carries an account name, which is routinely a shortened form of the registered vendor name. Jaccard penalises exactly the case that happens most.

Both name fields feed the index

174 of 1,077 vendors hold an account_name that differs from their vendor_name — sometimes the trading name, sometimes a person, occasionally the bank’s own name. Both are indexed, so a hit on either counts.

An account hit does not stop the name pass

Corroboration, not short-circuit

When an account hit and a name hit land on the same vendor, the account basis is kept (it is the stronger claim), the score becomes the higher of the two, and the name reason is added to the list shown to the reviewer. When an account is shared between vendors, the name is the only thing that can order the tied candidates.

The case that justifies weighting account highly

A live transfer to a person’s name resolved to a company vendor — findable only by bank account, because the beneficiary on the statement is an individual and the vendor in the master is a business. Weight account too lightly and that match stops standing out.

Two or more survivors = ambiguous

Nothing is auto-recorded. The resolved vendor is written onto the import row only when exactly one candidate survives — storing the top-ranked guess would turn a suggestion into a recorded fact nobody chose.

07Step 3b — Finding the payment

Pass A — the bank reference

Compare the normalised bank reference on the statement line against the normalised utr stored on approved payments. Every payment sharing that reference is collected into one group.

This is the only pass that can find a fan-out

One transfer sometimes settles several payments at once. Measured on live data: 40 such transfers covering 99 payments and 2.53% of all settled value — the largest a single ₹72,89,432 IMPS spanning 7 payments across 6 projects. Grouping by shared reference is what makes those visible as one event.

If Pass A finds anything, Pass B never runs. A direct reference hit is a key, not a heuristic; there is nothing a weaker signal could add.

Pass B — vendor + amount + date

Only reached when Pass A found nothing. Three conditions, all required:

i
The amount is within ₹1

See the ₹1 rule.

ii
The payment’s vendor is one of the resolved vendor candidates

A payment with no vendor of its own is skipped — “it matched because it had nothing to disagree with” is the wrong reason to offer anything.

iii
The payment date is within 3 days

A payment is recorded the same day 98.9% of the time, but month-end and weekend batches drift. Three days covers a Friday transfer recorded on Monday without reaching into the next week’s run. If either date is missing, the check passes — a row cannot be excluded on evidence that does not exist.

No vendor resolved ⇒ Pass B cannot run at all

It is “vendor + amount + date”. Without the vendor it degrades to “amount + date”, which against a ledger of 7,000+ payments matches far too much to put in front of a person.

Pass B is deliberately single-target

Each hit becomes its own one-payment group. A fan-out group’s members each hold a fraction of the bank amount, so an exact-amount pass can never reassemble one. Rather than guess at a partition — which would mean inventing an allocation nobody authorised — an unreferenced fan-out stays Unmatched and says so.

Why Pass B has to exist at all

932 of 7,420 Paid payments (12.6%) carry a utr that is not a bank reference at all: PO numbers, short numbers, and the literal string refund. Pass A cannot see any of those, so without Pass B they would all read as unrecorded money.

08Step 4 — Finding the expense

Expenses are searched differently, because the data supports different things.

Vendor cannot filter here, and that is a property of the data

Project Expenses.vendor is populated on 0.58% of rows, and Non Project Expenses has no vendor column at all.

So the gate is the amount, and the description text is used to rank:

CheckScoreNote
Amount within ±₹10.40the only gate — everything below is a bonus
The beneficiary’s account number appears in the description+0.40matched on digits only, so separators and a leading zero still hit
The payee’s name words appear in the description+0.20noise words excluded
The IFSC appears in the description+0.10

Total is capped at 1.0.

Where this signal comes from

Descriptions carry — inconsistently, but often — the payee’s name, account number or IFSC, typed in by whoever raised the expense. The one clean live match found during this whole exercise was discovered because an approved accommodation expense had the beneficiary’s account number typed into its description.

The consequence you will actually notice

Because the amount is the only gate, a round-number transfer that has an approved payment and an unrelated approved expense at the same amount honestly has two candidates — so it will be Matched but will not pre-select anything. On a ₹5,000 transfer this is common. That is the never-guess rule working as designed, not a bug.

09Step 5 — The verdict

The candidate list is: the best payment group (if any) plus every expense candidate. Then:

Candidates foundStatusWhat the row saysPre-selected?
none Unmatched No approved payment or expense matches this transfer. —
exactly one, holding one record Matched One approved record at this amount: PAY-… yes
exactly one, holding several (fan-out) Matched One transfer settling 3 approved payments: … no — no single record to name
two or more Matched 4 approved records match this amount: … Choose which one this transfer settled. no — the screen never guesses
There is deliberately no “Ambiguous” status

Both the confident and the contested case are Matched — something settleable was found, and a person confirms which. The distinction is a screen concern, carried in the note rather than in the vocabulary.

10The ₹1 rule

Exact-amount matching did not survive contact with a bank

31.4% of payments carry paise (2,370 of 7,556) while the bank sends whole rupees. In the first real import, three approved payments each sat within a rupee of the transfer that paid them — and every one came out Unmatched. The matcher was not broken; the rule was.

The three cases that changed the rule
Bank sentApproved paymentRecordedOff by
18,679.00PAY-00105-03818,678.690.31
21,925.00PAY-00105-03421,924.100.90
36,963.00PAY-00105-03536,962.320.68

The window is ₹1, inclusive at the boundary. That is exactly the width of the phenomenon: the bank rounds a paise amount to the whole rupee, so the gap is always strictly less than a rupee.

Why not wider

Anything wider starts absorbing differences that are not rounding. A ₹5 window would silently settle a payment that is genuinely ₹4 short, and nobody would ever see it.

One number, five places

The tolerance is applied by both SQL pool queries, by the matcher, by the write guard, and by the already-paid duplicate check. These are easy to change independently and catastrophic to change inconsistently: a pool wider than the guard offers a record the confirm then refuses; a guard wider than the pool silently permits a settlement the screen never proposed.

The fifth was missing until 2026-08-07 and cost 8 rows in a live statement — see the already-paid guard. If you are adding an amount comparison anywhere in this feature, it belongs on this list.

The difference is absorbed, not booked

Settling an ₹18,678.69 payment from an ₹18,679.00 transfer leaves the payment at 18,678.69 and marks it Paid. The 31 paise is not recorded anywhere. Accepted explicitly.

11What never matches, on purpose

CaseWhyWhat happens instead
Anything not Approved the import pays what is already approved; it never approves plain Unmatched, no nudge
TDS payments the bank sends amount − tds, which is thousands off. ₹1 cannot reach it and must not be stretched to. Worse, tds is written at fulfil time — so an approved unpaid payment has a blank one and there is nothing to subtract Unmatched; linked by hand. 709 of 7,421 Paid payments (9.6%) carry TDS
An unreferenced fan-out Pass B is single-target by design; inferring a group from amounts alone would invent an allocation nobody authorised Unmatched
A beneficiary resolving to no vendor Pass B cannot run without a vendor Unmatched; the expense pass still applies
Unmatched is not a failure state

Every one of these rows is fully resolvable by hand: the decision dialog browses all approved records across all three ledgers, independent of anything the matcher concluded. That escape hatch is the point — the matcher is allowed to be conservative precisely because nothing depends on it being complete.

12Three worked examples

A — the clean reference hit
Bank line
₹18,679.00 · ref 620918788160 · 28-Jul
  1. Eligible? Yes — SUCCESS, not seen before.
  2. Already Paid? No Paid payment carries this reference.
  3. Pass A — normalise 620918788160, compare against approved payments’ UTRs. One hit: PAY-00105-038 at ₹18,678.69.
    The 31-paise gap is inside the ₹1 window, so the pool query returned it in the first place.
  4. Pass A found something, so Pass B is skipped entirely.
  5. Expenses — none at this amount.
  6. Candidates: 1, holding 1 record.

Matched · pre-selected · the row reads “Matched PAY-00105-038 — tick to confirm”.

B — matched, but nothing pre-selected
Bank line
₹5,000.00 · a rent transfer · 28-Jul
  1. Pass A — no approved payment carries this reference.
  2. Pass B — the beneficiary is a person; a vendor is resolved, but no approved payment lines up on amount + date.
  3. Expenses — an approved Project Expense sits at exactly ₹5,000. Base score 0.40, plus a bonus because the payee’s name appears in its description.
  4. But a second approved expense also sits at ₹5,000, unrelated. Amount is the only gate, so it is a candidate too.
  5. Candidates: 2.

Matched · nothing pre-selected · the row reads “2 approved records match this amount… Choose which one this transfer settled.” The reviewer opens it and picks.

C — the TDS transfer
Bank line
₹1,96,000.00 · an electrical contractor · 28-Jul
The record
an approved payment of ₹2,00,000 with 2% TDS
  1. Pass A — the payment’s UTR is blank (it is not Paid yet), so no hit.
  2. Pass B — the vendor resolves and the date lines up, but the amounts differ by ₹4,000. The ₹1 window rejects it, and the pool query never returned it anyway.
  3. Expenses — nothing at ₹1,96,000.
  4. Candidates: 0.

Unmatched — and this is correct, not a miss. Nothing in the data says ₹1,96,000 and ₹2,00,000 are the same event: tds is only written when the payment is fulfilled, so at approval time the field is blank and there is nothing to subtract.

The reviewer opens the row, searches the vendor by name, sees the ₹2,00,000 payment marked with its ₹4,000 difference, and links it by hand — or settles it in the payments screen. Records outside the tolerance are shown and marked, never hidden, precisely so this is discoverable.
