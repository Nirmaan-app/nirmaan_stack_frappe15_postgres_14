ADR-0014 Amendment B
Revised BoQ carry, simplified

A row's decisions carry forward only if it is still in the same place with the same words. Nothing else. That one sentence replaces the entire description-matching engine.

1Why this amendment exists

The shipped carry matches a revision's rows to the original's on description identity alone, with no positional constraint. Two rows pair if their normalised description occurs exactly once on each side — row 3 can pair with row 900. It then follows the original's parent pointer and overwrites the fresh parser's parenting with it.

So when a revision inserts a new section heading, the rows beneath it still pair by description, their old parent still exists, no alarm fires — and the carry silently drags them back under the old heading. The newly inserted heading ends up childless, and every affected row renders as a calm Original.

The blast radius doubled on 20 July

Before commit d89153e8, the re-point was gated on human_parent >= 0 — it fired only for the ~13% of rows a human had manually re-parented. That fix (reading the effective value instead of the empty human-override layer) was correct in itself, but parent_node is always populated on a committed node, so the re-point now fires on every matched row, unconditionally. The fix removed the accidental limiter that was masking the design flaw.

The bug is currently a passing test

services/boq_revision/test_carry.py:95-113 — test_pcc_reparented_row_lands_on_twin_new_row_index — builds a revision with an inserted row and asserts that the carry beats the fresh parser. Its premise is that the parser is repeating a mistake. When the inserted row is a genuine heading, the parser is right and the original is stale — and the code has no input that could tell the two apart. This test must be rewritten, not preserved.

3The carry rule in full

The entire matching rule
same Excel row  +  same description
A row carries its decisions forward only if it is still in the same place with the same words.

3.1 · The two sides

OriginalRevision
Sourcecommitted BOQ Nodes, current version, mapped source sheetfreshly-parsed BoQ Review Rows
Positionsource_row_number — the Excel rowsource_row_number — the Excel row
Textdescriptiondescription
Excludedrows with a blank description. They carry nothing and demand nothing.

Text comparison = the description, trimmed, lowercased, internal whitespace collapsed. Nothing else is folded. Punctuation and synonyms are not normalised — in a BoQ, 1:4:8 versus 1:4:6 is a real change, and a fuzzy match is exactly what silently carries a wrong decision.

3.2 · A row is Copied when all three hold

  1. Its Excel row number appears exactly once on each side.
  2. The original row at that same Excel position has an identical normalised description.
  3. The original row's parent also satisfies (1) and (2) — or the original row is a root, which satisfies this trivially.

Then, and only then:

CopyFrom (committed BOQ Nodes)To (revision BoQ Review Row)
Classificationrow_class (already effective)classification — the parser layer
Parentparent_node → that node's Excel row → the revision row at the same Excel rowparent_index (-1 for a root)

Everything else is a normal parser row. No status is written, so the Status column shows Original — identical to a fresh upload — and every classifier warning, review flag, structural check and the finalize gate apply exactly as they always have (A9).

Why position is the whole safety argument

A parent always sits above its child, and any inserted or deleted row shifts every position below it. So the instant a row is introduced, nothing beneath it can satisfy condition (1) — the carry simply stops, and the fresh parser's answer flows through untouched.

There is no walk, no diff, no section-heading guard, no twin map and no ambiguity class. It is a keyed join on the Excel row number, and it makes the failure the amendment exists to fix structurally impossible rather than merely guarded against.

This is D6's explicitly rejected option — and that is the finding, not an oversight

source_row_number + description is named in ADR-0014 D6 and dismissed as "the same-file key — one inserted row shifts everything below ⇒ mass non-match ⇒ defeats the feature's whole point." D6 replaced it with description-only matching precisely to recover that lost yield.

That recovered yield is what made the carry unsafe. Description-only matching cannot distinguish "this row is unchanged" from "this row's surroundings changed underneath it", because it never looks at the surroundings at all. The amendment's central finding is that the yield D6 bought was bought with correctness, and is not worth it.

Recording it this way matters: a future reader will otherwise see a rejected option quietly reinstated and assume someone forgot to check.

3.3 · Never copied

  • level — always re-derived from the effective tree (ADR-0009). Copying it fires the BOQ Nodes controller throws.
  • Human-layer fields (human_classification / human_parent / human_is_root) — the copy lands in the parser layer, so the row renders "Original" (calm), has_override stays false, Apply-AI stays available sheet-wide, and the subtotal_marker / header_repeat vocabulary gate is sidestepped.
  • Anything on a non-matched row.

3.4 · The status field

revision_carry_status holds Copied, or nothing at all. It is a stored value; what the user sees is the Status column, whose existing bottom rung already renders Original when the field is empty. So a non-copied row on a revision looks exactly like any row on a fresh upload — which is the point.

Storing the literal string "Original" was considered and rejected: it stops the field being inert for non-revision BoQs, so every upload and template sheet would need new gating code just to keep behaving the way it already does.

New, Ambiguous and Drifted are retired. Their Select options stay in the doctype JSON but are never written again — the precedent Drifted already set.

Copied ⟺ matched ⟺ rate-eligible. One equivalence, one number, end to end.

Scenario 7

Symmetric with scenario 5. Rows above row 6 copy; the deleted row simply has no counterpart; everything below shifted and falls to the parser. A deletion is as disruptive to the key as an insertion, and deliberately so — both move every position beneath them.

Scenario 9 · accepted regression
Two whole sections swapped in order

The estimator moves Electrical above Civil works. No text changes at all — but every row moves.

Near-zero carry. Today's description matcher would pair all six rows regardless of position; that is exactly the behaviour being removed, and it is what makes scenario 6 wrong. A wholesale reorder is rare in a revision; an inserted heading is not. Accepted trade, recorded deliberately.
Scenario 10 · the one hole
A heading inserted and a row deleted in the same span

A heading is inserted at row 10 and a row is deleted at row 20. Rows 21 and below shift down by one, then back up by one — landing on their original Excel positions with their original text.

Those rows satisfy all three conditions and will copy a parent that the new heading should have taken. It requires a net-zero row change across the span, with a heading among the insertions. Narrow, but real. Documented as a known hole, not engineered around — closing it would mean reintroducing a span scan, which is the complexity this amendment exists to remove.

Bonus — a sheet with no source. A tab the mapping screen marked "new", or one whose source had nothing committed: no carry runs, no revision chrome appears, and the sheet behaves exactly like a fresh upload.

6Entry & config decisions

A1 — The entry never locks
Upload always creates a plain draft. Origin (New / Revise) and the chosen original are set after the upload, not baked into it.Owner-confirmed

Today source_boq rides the upload POST, and the backend bakes three things at insert time: the origin fields, the boq_name copied from the original, and — driven by that name — the auto-bumped version, plus whether the sheet drafts get seeded at all. So the frontend freezes the radio the instant the POST fires (BoqMasterPanel.tsx:70, entryLocked = uploadStatus !== "idle").

Because the default is New, dropping a file first immediately fires a fresh upload and the Revise option becomes permanently unreachable. There is no server-side guard forcing this — the lock is entirely a frontend invention. ADR-0014 line 72 already specified “single screen, order-independent”; the implementation delivered it only inside the pre-upload window.

STEP 1
Drop the file
Uploads and parses immediately as a plain draft. Nothing about origin is decided.
STEP 2 · any order
Pick New or Revise
Radio and picker stay live throughout, and can be changed back and forth.
STEP 3 · new endpoint
Continue
Converts the draft: sets origin + source, rewrites boq_name, recomputes version, clears the auto-seeded drafts.

The one sharp edge: the version recompute must mirror the before_insert hook exactly (MAX(version)+1 scoped to project + boq_name), because that hook has already run against the filename-derived name by the time we convert.

A2 — Config lands Pending
Seeding carries the original's rectified column map, header row, area dimensions and work packages — and always writes wizard_status = Pending.Owner-confirmed

The clean-versus-unsafe column diff still runs; it just becomes advice rather than a status. Nothing downstream distinguishes an auto-marked sheet from a user-marked one, so the only behavioural cost is that the hub's Parse button stays disabled until the user marks at least one sheet — which is the intent.

One thing that must ride along

Carried drafts currently get no work package — the fresh-upload path auto-detects it, revision seeding does not. The Config-Done attestation checkbox is disabled without one, so leaving sheets Pending would force the user to re-pick a work package on every single sheet. The amendment therefore also carries the work_packages child rows from the original's draft.

7Open — needs your call

The rate-carry version pin the only remaining blocker

Confirmed live at branch tip, and not caused by this rework. The cross-BoQ rate carry reads the source's pricing pinned to that sheet's current commit_version. But re-committing a sheet orphans its pricing onto the now-frozen version — the commit pipeline says so in a comment and does not migrate it. So a source priced at v1 and then re-committed to v2 carries zero rates, while the mapping screen cheerfully promised three.

Two ways out: align the carry read to is_current (freshest, matches the count), or keep the pin and make the count match it plus prompt “run Copy rates forward on the original first”. Without a decision here, “copied rows can directly get the filled rates” fails on day one.

Related oddity to settle at the same time: BoQ Sheet.source_commit_version is stamped at commit as a durable provenance pin and then read nowhere in the entire branch. It is currently write-only.

Two earlier open items are now closed by the rule itself

  • The rootness guard — a heading inserted above a section shifts it, so it cannot copy anyway. The question dissolves; there is nothing to guard and nothing to advise about.
  • Strict versus loose Copied — classification and parenting now always carry together or not at all (A4), so there is no case left to distinguish.

9What is not changing

  • The revision is still a new BOQs doc with origin="revision" and a source_boq pointer, auto-bumped to v(N+1). The original stays frozen as the diff baseline (D2, untouched).
  • Sheet pairing — the mapping screen, its N2 proposal, the human confirmation, and the write-once source_sheet_name pointer (D3, untouched).
  • The commit overlay's carry taxonomy — amount formulas, remarks, colours, remark dismissals and the whole category layer carry; the four computed dismissals and reconciliation choices never do (D8, untouched). Only its reporting changes, and its row pairing now uses the same position key.
  • The finalize gate stays purely structural with no override path, and no revision-specific condition. Marking a sheet finalized is the human sign-off, not a second gate.
  • The merge seam — the carry still runs inside the parse worker, after the review-row insert loop and before the sheet is marked Parsed, in the same transaction.
  • Rate carry remains one explicit post-commit action from the hub footer, per-sheet isolated, destination-locked, never ambient at commit.
  • Every non-revision flow stays byte-identical. Every seam is gated on origin == "revision".

A structural bonus worth naming

There are two matcher runs in the chain: one at the parse seam over review rows, one at the committed tier that drives both the annotation overlay and the rate carry. Today they can legitimately disagree — the committed run is fed the effective nesting depth while the parse run is fed parser level, and a human re-parent between review and commit changes one and not the other. So “matched at review” and “matched at commit” are not the same set.

Under a position key that divergence becomes impossible by construction: the Excel row number and the description are both immutable after parse, and neither is a function of the tree. The two runs are provably identical — which is what makes “re-derive the Copied set at the committed tier” a safe choice rather than a hopeful one. The committed-tier matcher already keys on source_row_number today, so it barely changes.
