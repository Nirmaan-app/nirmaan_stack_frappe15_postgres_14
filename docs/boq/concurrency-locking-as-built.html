Why this exists — two verified hazards

The BoQ wizard is multi-user, but before this branch it had almost no concurrency control — only the pricing editor held a lock, and even that never notified anyone. Two distinct, adversarially-verified hazards drove the work.

Hazard 1 — Commit duplicate-is_current race _next_commit_version reads max(commit_version)+1 on a plain read, then freeze-then-inserts with no SELECT FOR UPDATE, no in-progress flag, no unique index. Two concurrent commits of one (boq, sheet) both write is_current=1. Every downstream pricing read resolves the sheet by is_current=1 (not max(version)) — so a duplicate silently and non-deterministically corrupts the invariant the whole pricing layer depends on.
Hazard 2 — Cross-stage "rug-pull" BoQ phases are a one-way ladder (Config → Review → Commit → Pricing/Tendering), but every backward endpoint is a role-less @frappe.whitelist, and every existing guard is a user-agnostic forward freeze. A user in an earlier stage can Force Re-parse + re-commit a sheet another user has priced. Pricing keys on committed_version; a re-commit mints v+1, freezes the prior, and the editor only ever loads is_current — so the downstream pricer's work is silently orphaned on the frozen version (invisible), recoverable only via partial copy-forward (rates only; formulas / remarks / colours lost).

The three-dimension model

Rather than invent a subsystem, the build reuses in-house patterns across three orthogonal dimensions. Each answers a different question.

DimensionQuestion it answersScopeBuilt from
Draft-tier lock (same-stage)Is a peer editing Config/Review of this sheet now?(boq, sheet)Pricing-lock engine, version=0 sentinel
Pricing lock (same-stage)Is a peer pricing this committed version now?(boq, sheet, version)Existing lock + new realtime layer
Directional guard (cross-stage)Does a later stage hold work my earlier action would orphan?Across the ladder5 targeted existence checks

The single-editor lock is a fused primitive: the pricing lock's enforcement core (deterministic-PK acquire → exactly-one-winner) + a realtime layer (boq:lock_changed broadcast) + a cleanup layer (heartbeat + sendBeacon release). A server-side break-glass flag (boq_locks_disabled, default enforcing) can disable all of it in prod.

Shipped features

A1

Commit-race fix

Shipped

Makes "exactly one is_current per (boq, sheet)" a database guarantee, not a convention — and serialises concurrent commits for clean UX.

Mechanism — defence in depth
  • Durable backstop: a partial unique index (boq, sheet_name) WHERE is_current=1 on BoQ Sheet and (boq, source_sheet_name) on the grid tier. A concurrent duplicate INSERT now fails with IntegrityError (caught per-sheet → reported in failed[]) instead of corrupting.
  • Graceful UX: a per-BoQ PostgreSQL advisory lock (pg_try_advisory_lock) serialises commits, so a 2nd concurrent commit computes N+2 rather than colliding on N+1.
  • Heal-then-constrain migration: before adding the index, demote any pre-existing duplicate — keep the highest commit_version, never delete frozen history.
patches/v3_0/boq_commit_current_unique_guard.py
# CONSTRAIN — a duplicate is_current INSERT now fails at the DB, cannot corrupt
CREATE UNIQUE INDEX IF NOT EXISTS uq_boq_sheet_current
    ON "tabBoQ Sheet" (boq, sheet_name) WHERE is_current = 1;
commit_pipeline.py — graceful serialization
if not frappe.db.sql("SELECT pg_try_advisory_lock(%s)", (_commit_lock_key,))[0][0]:
    # another commit of this BoQ is in flight — reject cleanly, corrupt nothing
    frappe.throw("A commit for this BoQ is already in progress…")
# … released in a finally: block, on both success and failure paths
NoteThe index (not the flag) is the real guarantee — it holds even across workers and check-then-set gaps. Live data was clean at authoring time, so the heal is a safety net for other environments.
A2

Realtime single-editor pricing lock

Shipped

The pricing lock already enforced (server throw) but never notified — a 2nd user learned only on a failed save, and a holder who left stranded the sheet for 5 minutes. A2 adds the realtime + cleanup layer.

Mechanism
  • Acquire on first edit-intent — the grid's first dirty keystroke calls acquire_pricing_lock (not on mount, not on save).
  • Broadcast boq:lock_changed after commit → every open pricing screen flips read-only / frees live, sub-second.
  • Cleanup — a ~30 s heartbeat refreshes the lock while held; navigator.sendBeacon releases it on unload/unmount; a ~2-min edit-driven TTL frees a hard-crash lazily.
  • Reject writes nothing — a 2nd writer gets BOQ_PRICING_LOCKED and the server mutates nothing.
pricing_lock.py — the broadcast (reused by the draft tier too)
def broadcast_lock_changed(boq, sheet_name, version, action, locked_by):
    # caller must frappe.db.commit() FIRST (commit-before-publish)
    frappe.publish_realtime(
        event="boq:lock_changed",
        message={"boq":boq, "sheet_name":sheet_name,
                 "version":version, "action":action, "locked_by":locked_by},
    )
Worked example — two users, one committed version
t0
User B opens the pricing screen — sees rates, editable.
t1
User A types the first rate → acquire_pricing_lock ✓, broadcast acquired.
t1+200ms
User B's screen flips read-only with "🔒 Being edited by Administrator" — no refresh.
t2
User A navigates away → sendBeacon release, broadcast released.
t2+
User B's screen re-enables live.

B1

Draft-tier single-editor lock (Config + Review)

Shipped

Config/Review collisions are destructive (whole-blob clobber, cross-row tree corruption). B1 extends the same locking primitive to the draft tier — with no new doctype and no migration.

The elegant trick Reuse the BoQ Sheet Pricing Lock doctype with a sentinel committed_version = 0. Real committed versions start at 1, so the draft identity sha1(boq ␀ sheet ␀ 0) is disjoint from every pricing-lock identity. One engine, two tiers, zero schema change.
Mechanism
  • Acquired on first edit-intent in every draft write endpoint — config writers, review edit / restructure / revert, and the AI-accept writers — after the existing freeze guards, before the write.
  • Spans Config ↔ Review of one (boq, sheet). It is not keyed on wizard_status (which flips mid-edit); the version=0 sentinel is stable across the whole draft lifecycle.
  • Annotation-only writes (save_review_remark, dismiss_row_flags) do not acquire — a remark is not an edit.
  • Distinct BOQ_DRAFT_LOCKED marker lets the frontend tell a draft reject from a pricing reject.
draft_lock.py — thin wrapper over the shared engine
DRAFT_LOCK_VERSION = 0            # sentinel — never collides with a real version (≥1)
_DRAFT_MARKER = "BOQ_DRAFT_LOCKED"

def acquire_or_refresh(boq, sheet_name, user, now):
    return pricing_lock.acquire_or_refresh(
        boq, sheet_name, DRAFT_LOCK_VERSION, user, now,
        marker=_DRAFT_MARKER, activity="edited",   # reuse the pricing engine verbatim
    )
✓ Verified liveReview edit → acquire_draft_lock [200], DB row with committed_version=0. User B's Review screen flipped read-only instantly. Cross-screen invariant proven: the lock acquired via Review also made the Config screen read-only for User B — one lock, both stages.
B2

"Who else is here" presence overlay

Shipped

Presence ≠ lock. A complementary BoQ-level awareness badge (built on Frappe-core doc_viewers) shows who else has the BoQ open — on all four screens (hub, config, review, pricing).

Why it is separate from the lock

Presence has no ownership and no server reject — you cannot build a write-block on "who has the doc open" (the PR app proved this: its input-block was coded and deliberately commented out). So presence stays purely informational; enforcement is the lock's job.

✓ Verified live"Also here: Nived K K" rendered on all four screens, both directions, in realtime.
B3

General-specs compare-and-set

Shipped

The hub general-specs Save is replace-all (delete-then-reinsert). Two users editing the ticked set concurrently would silently clobber each other. B3 turns that silent lost-update into a visible, recoverable conflict.

Mechanism — optimistic concurrency

The client sends expected_current — the set it loaded. The server compares it to the live DB set; if they differ (a concurrent change), it rejects instead of clobbering.

update_sheet_draft.py :: set_general_specs_sheet
if current != set(expected_current or []):
    frappe.throw(
        "The general-specs selection was changed by someone else since you "
        "loaded it. Reload the BoQ and re-apply your change.",
        title="Selection changed",
    )
✓ Verified liveClient payload carried expected_current:["MAKES"]; a stale baseline threw "Selection changed"; matching baseline saved. Set unchanged — no clobber.
C0

Directional guard — the state floor

3 of 5 wired

The cross-stage dimension: turn the silent rug-pull into an explicit, acknowledged action. An earlier-stage endpoint that would orphan downstream pricing throws BOQ_DOWNSTREAM_ORPHAN (with the exact count) unless the caller passes an explicit confirm flag.

directional_guard.py — pure existence check, writes nothing
ORPHAN_MARKER = "BOQ_DOWNSTREAM_ORPHAN"   # stable token the frontend switches on

def guard_no_downstream_orphan(boq, sheet_name, confirm, action):
    count = downstream_priced_count(boq, sheet_name)   # priced cells on is_current version
    if count and not _truthy(confirm):
        frappe.throw(
            f"{ORPHAN_MARKER}: '{sheet_name}' has {count} priced cell(s) on the "
            f"current committed version. A {action} will orphan them… Confirm to proceed.",
            title="This will orphan priced cells",
        )
    return count   # 0 ⇒ free forward progress, no guard
Frontend contract

Each endpoint gets a confirm_orphan param. The reject mutates nothing. The frontend detects the marker → shows an AlertDialog ("This will orphan priced cells… Re-commit anyway / Un-finalize anyway") → on confirm, retries with confirm_orphan=true. CommitDialog.tsx is the reference implementation.

✓ Verified liveBoth wired guards fired the exact dialog with count 7; Cancel left v1 intact (no v2 minted); confirm_orphan=true bypass worked. Backend also proven at the endpoint level (rolled back).
Design note — why only 3 of 5 are correctness-critical The orphan is only realized at re-commit (and root-metadata). The other endpoints (un-finalize, force-reparse, review edits) are gateways — remove their guards and the re-commit keystone still catches the orphan at the moment it actually happens. So the two pending guards are early warnings, not the last line of defence.

Pending — and why each is still needed

Phases A and B are complete and E2E-verified. Phase C is ~60% (3 of 5 guards, flat confirms). Here is what remains from my end, ordered by leverage, each with the reason it is still needed.

C0·rest

The 2 unwired directional guards

Pending · low urgency

Force-reparse (run_parse) and the Parsed-reviewer window (save_review_edit et al.) still have no confirm_orphan gate.

Why still needed They are early warnings — they surface the orphan risk at the moment the user starts the regression, not only at the final commit. Without them a reviewer can quietly re-parse and rework a priced sheet and only hit the wall at re-commit, having already lost their intermediate context. Not correctness-critical (the re-commit keystone is the backstop), so this is genuinely descope-able if you prefer the minimal surface. Note: do parse_run.py by hand — a prior automated edit broke that large file.
C1

Presence-escalated warning — amended (ADR-0011 A1)

Pending · design locked

The amended C1 keeps the guard warn-only — no blocks — and enriches it with a live name + an on-entry banner. This supersedes the earlier tiered-block / attribution design (grill Q1–Q9).

  • Enrich the message with the Live name — the guard also reads the pricing lock: a fresh other-user lock → "X is pricing v{N} now — proceeding orphans their {count} cells"; else count-only (Vacated); a self-held lock → count-only. No attribution schema — the name comes free from the lock.
  • On-entry banner — persistent banner on Review / Config, a per-sheet card indicator on the Hub, a note by the root-metadata controls; the interrupting modal is reserved for save.
  • Wire the 2 pending guards as warnings — force re-parse = a decisive modal; review / config edits = a first-edit-of-session ack (not per-keystroke).
  • Dropped: the hard block, the Author-or-Admin role check, and the committed_by/priced_by fields + migration.
Why still needed It delivers "no-one should accidentally alter another phase's work": an unmissable, named warning at entry and at save. Warn-only means orphaning stays possible but never silent; the existing freeze + copy-forward keep it recoverable. Detection is already shipped (the 3 confirms) — this is the message enrichment + banners + the 2 remaining guards, re-cast as warnings.

The open design question

A reassessment surfaced: given that locks, finalization and the commit pipeline already exist, do we still need the directional guard at all? The verified answer is yes — none of the existing mechanisms covers this, because they are all same-stage or preservation, and the concern is cross-stage.

Existing mechanismWhat it protectsBlocks upstream alteration of a priced sheet?
Draft lock (v0) + Pricing lock (vN)Two people editing the same stage at onceNo — the two locks live on different version keys and never see each other; commit_boq never checks the pricing lock.
Finalization freezeCasual review edits while FinalizedNo — un-markable, and it is the gateway to the rug-pull; it does not gate re-commit.
Commit pipeline (freeze-and-supersede)Preserves prior versions as historyNo — it is the source of the orphaning; role-less, never asks "is this version priced?"
Resolved — Amendment A1 (grill Q1–Q9) Keep the guard, but make the response a presence-escalated warning, never a block — the owner reframed "no-one should be able to alter" as "no-one should accidentally alter". Detection stays the state floor; a fresh other-user pricing lock escalates it to a named warning; the user may always proceed after acknowledging. This drops the hard block, the Author-or-Admin gate, and the attribution fields + migration. Full model + grill trail: docs/adr/0011-boq-concurrency-locking.md § Amendment A1.
