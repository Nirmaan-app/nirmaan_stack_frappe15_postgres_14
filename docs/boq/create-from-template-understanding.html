Analysis · pre-grill

Create BOQ from Template

My understanding of the requirement, mapped against the current BOQ upload pipeline — before we /grill-with-docs to close the gaps.

1 · The requirement, restated

Add a second entry option next to Upload BOQ: Create BOQ from Template. The template is a pre-built workbook (MEP BOQ..xlsx). Its sheets become a menu the user picks from to compose a brand-new BOQ.

  • Config + parsing are pre-baked into the template — the user skips the per-sheet Configure and Parse steps entirely.
  • After picking sheets, the user lands in the Sheet Hub. Per sheet, instead of Configure→Parse, he opens a Review-and-Select screen where classification & parenting are already done.
  • He selects the eligible rows he needs. Selection is smart: deselecting a preamble deselects every item nested under it.
  • He can create new rows above/below any row — but must supply their classification and parent.
  • He fills quantities for the selected eligible rows (eligibility follows the pricing priceability ruleset).
  • He finalizes the sheet. Everything downstream (commit → tender → pricing) works exactly as today.

Net effect: a "build a BOQ from scratch, off a curated skeleton" path, versus the "ingest a client's Excel" path we have now.

Two facts that shape the whole design

① Every sheet has a different column map & header-row count. There is no single global config — each template sheet must carry its own pre-baked sheet_config (header rows, column roles, areas, work packages). This is exactly the per-sheet sheet_config blob the Configure spoke produces today.

② Hierarchy is encoded in column A — roman/letters (i, ii / A, B, C) = sections/preambles; 1.0, 2.0 = groups; a, b = line items; plus explicit …TOTAL / TOTAL CARRIED OVER subtotal rows. This is precisely the classification + parenting the template pre-computes so the user can skip Parse.

Note: the template rows carry real quantities and rates — it is a completed reference BOQ, not an empty skeleton. What we keep vs. strip is an open question (§6-C).

3 · Current pipeline (as-is) — where template branches off

Upload .xlsx→ Ingest worker: create BOQs + sheet_drafts + auto-guess config→ Hub
per sheet: Configure spoke→ Mark Config Done→ Parse run → BoQ Review Rows→ Review (reclassify / reparent)→ Finalize (hard gate)→ Commit → Tender / Pricing

Status machine on BoQ Sheet Draft.wizard_status: Pending → Config Done → Parsed → Finalized, then Commit builds versioned BOQ Nodes. The hub, commit, and tender machinery are entirely status-driven and template-agnostic — they don't care how the rows got there.

Proposed template pipeline (to-be)

Pick "From Template"→ Choose sheets (checkbox list of the 9 trades)→ Clone template → BOQs + sheet_drafts (config pre-set) + cloned BoQ Review Rows→ Hub
Configure Parse then per sheet → Review + Select + Qty (enhanced review)→ Finalize→ Commit → Tender / Pricing (unchanged)

The clean seam: the template flow replaces "upload → config → parse" with "clone template rows", arriving at a sheet that is effectively already Parsed. It then converges on the identical Review → Finalize → Commit spine. The quantities the user enters land on the review rows (qty_total / qty_by_area) so the existing commit step captures them onto BOQ Nodes — same as an edited parsed sheet today.

5 · The priceability rule I'd reuse for "which rows accept a quantity"

From PricingGrid.isRateEditableRow / priceability.ts (owner-locked, asymmetric):

eligible iff  override  OR  node_type === "Line Item"  OR  (node_type === "Preamble" AND row is qty-bearing)

  • Line Item — always a qty target (even a zero-qty "rate-only" line stays editable).
  • Preamble — only when it already bears a quantity; a plain grouping preamble is read-only.
  • Other (note / spacer / subtotal / header) — never, unless overridden.

Nuance to resolve: today this gate assumes qty already exists. In the template flow the user is supplying the qty — so the natural target set is Line Items (and qty-bearing Preambles from the template). Multi-area sheets (Electrical) raise per-area-vs-scalar entry — §6-F.

6 · Open questions for the grill

These are the forks where the design genuinely branches. My lean is marked in green; I'll bring them into /grill-with-docs.

A · Template storage model. How is the template "registered"?  Lean: a curated BoQ Template + BoQ Template Sheet doctype holding the per-sheet sheet_config and a canonical, pre-classified/parented set of template rows — authored once by running the workbook through the normal upload+config+parse pipeline, then frozen. "Create from template" clones those rows into a fresh BOQs. Generic (a template library) so admins can add more later, but MVP seeds only the MEP one.  Alternative: ship the xlsx as a fixture and re-parse on each create (couples create-time to a live parse + a source file).
B · Selectable sheets. Confirm Summary (rollup) and Make List (reference) are excluded, leaving the 9 trade sheets. Lean: exclude both.
C · Do template rows carry rates? quantities? The template has both filled in. Lean: strip both — the template provides structure + classification + parenting + units + column config only; the user supplies quantities now, and rates stay for the pricing/tender stage as today.  But you may want the template rates as default estimates — that's a real product call.
D · Selection cascade — both directions? Deselect preamble → deselect subtree (given). Does selecting a child auto-select its ancestor preamble (to keep a committable tree, matching structural error #8 "line item parent must be preamble")? Lean: yes — auto-pull ancestors in on select.  And default state: all-selected (prune down) vs none-selected (opt-in)? Lean: all-selected.
E · Create-new-row primitive. This is the biggest net-new piece — no insert/delete endpoint exists today. Questions: row-index strategy (re-index the sheet vs fractional/synthetic indices — note row_index is the parent-pointer key space); is delete also needed, or only insert? does a created row participate in the same finalize gate? Lean: synthetic row_index (like is_synthetic rows), insert-only + deselect-to-exclude instead of hard delete, full gate participation.
F · Quantity input surface & multi-area. Where does qty entry live — inside the enhanced Review screen, or a distinct step? For area-split sheets (Electrical: Washroom / Office space) does the user fill per-area quantities (into qty_by_area) or a single scalar (qty_total)? Lean: qty entry inline in the same select screen; honor the template sheet's area config — scalar sheets get one qty cell, multi-area sheets get per-area cells.
G · One screen or two? Is "review + select + create + qty" one enhanced screen, or is Select separate from Qty? Lean: one screen, progressive — a selected checkbox column + inline qty inputs on the existing ReviewTree, gated read-only affordances flipped on. Reclassify/reparent affordances stay available for created rows.
H · Amount formulas for pricing. Tender/pricing needs a covering amount-formula per amount column before rates are editable. Are these pre-baked in the template too (they're derivable from the Supply/Install amount columns)? Lean: yes — bake amount formulas into the template config so the priced sheet is edit-ready with zero extra setup.
I · Work packages & general specs. Template sheets carry work-package associations in their config (Section 4). Auto-carry on clone? Lean: yes. No general-specs/preamble-master sheet is evident in the template — assume N/A unless you flag one.
J · Coexistence with Upload. A single BOQ mixing template sheets and uploaded sheets — allowed, or are the two entry paths mutually exclusive per BOQ? Lean: keep them separate per BOQ for MVP; revisit mixing later.

7 · What I'm confident about vs. what needs your input

Confident

  • The convergence seam: template flow reuses Review→Finalize→Commit→Tender unchanged.
  • Per-sheet pre-baked config is required (sheets are heterogeneous).
  • Selection tree + cascade reuse the existing flat-row / effective-parent model & DFS.
  • Eligibility follows the existing priceability rule.
  • Row-create and qty-input are genuinely new surfaces with no current analog.

Needs your call

  • Template as a stored doctype vs. re-parsed fixture (A).
  • Keep/strip template rates & quantities (C).
  • Cascade direction + default selection (D).
  • Row-index strategy & whether delete is in scope (E).
  • Per-area vs scalar qty entry (F).
  • Template vs upload coexistence (J).
