# Billing Executive role — a view-only mirror of Estimates Executive, minus pricing and BoQ

`Nirmaan Billing Executive` is a role whose backend Role + Role Profile already existed in fixtures (with read permissions pre-seeded on ~77 doctypes) but had **zero frontend wiring**. We wired it as a **view-only mirror of Estimates Executive** — same sidebar, dashboard, and view-only page gates — with two deliberate exclusions: the **Pricing module** (HVAC / Electrical / ELV) and **BoQ** (Upload BoQ, BoQ Templates, the BoQ project tab, and every BoQ doctype). Rule of thumb: everywhere the code reads `Nirmaan Estimates Executive Profile`, the Billing profile sits beside it — EXCEPT the two pricing gates (`NewSidebar` pricing spread + `PricingRoute`) and the BoQ surfaces.

**What is in the repo:** the frontend wiring (role registry, dashboard, sidebar, the view-only `isEstimatesExecutive` gates, the `isBilling` BoQ-tab hide) and two backend code gates — `api/projects/tendering.py` (Billing may manage tendering) and `api/sidebar_counts.py` (Billing gets un-project-filtered counts). Billing's **baseline doctype read permissions** were already seeded in fixtures on ~77 doctypes; since Billing is **view-only**, read is functionally all it needs, so no doctype-permission change is *required* for the role to work.

**What is DATABASE-ONLY (not in the repo):** three runtime permission adjustments were applied but are **not committed**, so a fresh site or a prod restore-from-backup silently lacks them.

1. **8 transactional doctypes** (Customers, Delivery Notes, PO Delivery Documents, Procurement Requests, Project Inflows, Project Payments, Quotation Requests, Vendor Invoices) upgraded read→RWCD, plus **Commission Report Template Snapshot** granted read — applied via `reload_doctype`. The doctype-JSON edits that would have carried these in the repo were **deliberately reverted** (the "Don't Touch doctype JSONs" convention), so these live only in the DB and a `bench migrate` would reset them to the fixture/JSON state. (Low impact: Billing is view-only, so the RWCD upgrades are parity-only, not functional.)
2. **`Nirmaan Item Units`** (read) and **`Material Delivery Plan`** (read) granted via **`Custom DocPerm`**. These two doctypes carry `Custom DocPerm`, which in Frappe **fully overrides** the standard `DocPerm` shipped in the JSON — so a JSON/fixture grant is inert against them; only a DB `Custom DocPerm` row takes effect. `Nirmaan Item Units` is a 16-row units lookup that several finance/procurement pages fetch — the original bug report ("No permission for Nirmaan Item Units") was exactly this. The Estimates *role* also lacks Item Units (Estimates users only read it because they additionally hold `System Manager`), so granting Billing read is a small, deliberate step **beyond** the strict Estimates mirror.

## Considered Options (persisting the DB-only permission changes)

- **Doctype JSON / fixtures** — rejected: hand-editing doctype JSONs violates the "Don't Touch" convention (and the edits were reverted for that reason), and `Custom DocPerm` cannot be expressed as a standard-`DocPerm` JSON row anyway — shipping a `Custom DocPerm` **fixture would overwrite production's hand-tuned Custom DocPerm** for other roles (a standing project rule).
- **A migration patch** — viable and repo-portable (runs on `bench migrate`); deferred in favour of the immediate DB grant to unblock testing. This is the natural way to make these travel automatically if that becomes necessary.
- **DB now (chosen)** — applied directly to the running site (`reload_doctype` for the standard perms, Role-Permission-Manager mechanics for the two Custom DocPerm reads), so testing was unblocked immediately.

## Consequences

- **A fresh site or a prod restore-from-backup silently lacks the DB-only changes**, and the "No permission for Nirmaan Item Units" error reappears. **Reapply on every new environment** via **Role Permission Manager**: add role `Nirmaan Billing Executive` with **read** on `Nirmaan Item Units` and `Material Delivery Plan`. The 8 RWCD upgrades + Commission read are parity-only and optional to reapply (view-only role); reapply them too only if strict Estimates parity is wanted.
- **Everything a view-only Billing user actually needs to function is either in the repo (frontend + the two API gates) or in the pre-existing fixture read perms** — except `Nirmaan Item Units` / `Material Delivery Plan` read, which are the two that MUST be reapplied on a new env.
- "Beyond the mirror": Billing read on `Nirmaan Item Units` exceeds what the Estimates *role* has. If the Estimates role is ever corrected to include Item Units, revisit whether Billing should track it or stay independent.
- The BoQ exclusion is enforced in several places at once — the sidebar, the BoQ template-authoring gates (frontend + backend), the (reverted) BoQ doctype perms, and the per-role BoQ project-tab hide (`project.tsx` `isBilling`). Keeping BoQ out of Billing means keeping all of these in sync.
