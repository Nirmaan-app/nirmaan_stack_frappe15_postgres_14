# 15. Cashbook import creates expenses nobody approved

Date: 2026-08-13

## Status

**Accepted — owner-ruled 2026-08-13**, over a 24-question grilling (Q1–Q24) against a real 137-row
petty-cash export. Numbered `0015` (highest existing is `0014`; the historical `0002`/`0007`/`0008`/
`0014` collisions are **not** renumbered — out of scope).

Build record: `frontend/.claude/plans/outflow-import-plan.md`. As-built detail:
`.claude/context/domain/outflow-import.md` § Cashbook. Feature spec (Cashfree, unchanged):
`docs/outflow-import/workflow.html` § 0.

## Context

Bulk Import Outflow has one prime directive, stated in bold in its domain doc:

> **The import PAYS what someone has already approved. It never approves, and it never creates a
> `Project Payment`.**

Every rule under it follows from that. Only `Approved` records are matched. The ±₹5 window exists
because a settle must land on a record a person already sanctioned. `Outflow Row Match` records
settlements only. The whole feature is a payment reconciler.

**Cashbook is a petty-cash wallet export, and it has no counterpart to settle.** A ₹180 auto fare
paid from a site engineer's wallet was never raised as an expense, never approved, and exists
nowhere in the system until the statement arrives. There is nothing to match. The only useful thing
to do with the row is CREATE the record it describes.

Two structural facts make it a different animal from a bank statement:

- **It carries no UTR, no beneficiary account and no IFSC.** Match tiers 0 and 1 read exactly those
  fields, so the ladder is not merely unhelpful here, it is inoperable. The one thing it *could*
  find is a real approved payment that happens to share an amount.
- **Its remarks are typed by a person, not generated by a gateway.** Cashfree writes
  `paytm bangalore materials`; a wallet user writes `Food expenses paytm project` or
  `Locally purchased for VR mall`.

## Decision

**Cashbook rows create `Project Expenses` and `Non Project Expenses` directly at status `Paid`,
without an approval step, in one confirmed bulk action.**

The prime directive is amended to be **source-scoped** rather than absolute:

> A **Cashfree** import pays what someone has already approved; it never approves and never creates.
> A **Cashbook** import creates what a wallet already spent; it never settles an existing record.

Neither source may do the other's job. `api/outflow_import/cashbook.py` never calls `match_batch`,
and a test reads its AST — not its source text — to keep that true.

### Why this is narrower than it first reads

`Project Expenses.validate` already auto-approves any positive amount **under ₹5,000** on creation.
On the measured statement that is **113 of 115 rows**. The genuinely new territory is two ₹6,000
rows a fortnight, not a hundred.

### What was measured before deciding

| | |
|---|---|
| Rows in the export | 137 (115 wallet spends, 16 balance movements, 6 totals lines) |
| Rows resolving to a project | 87 |
| Rows resolving to none | 28 |
| Falling back to `Petty Cash` | 26 (22%) |
| Misfile rate, existing matcher | ~16% |
| Misfile rate, after the Q13 fixes | **~1–2%** |

## Consequences

### Accepted risks

Each was raised with evidence and reaffirmed. They are recorded here so they read as decisions.

**R1 — nothing can be corrected before it is written (Q2).** The review step is READ-ONLY. Roughly
one or two rows per statement land on the wrong project, unseen. The correction path is editing the
expense in the Expenses module afterwards (Q12), which nothing prompts anyone to do.

*Mitigation, and it is real but partial:* the review tree groups by project and orders by value, so
one-row groups gather at the bottom — the shape a wrong match takes. On the measured statement both
known bad matches landed in the last seven lines of a fourteen-line list. A reader who scans can
find them; a reader who does not, cannot.

**R2 — a row nobody can place is still booked (Q14).** A blank remark and a two-project remark both
become Non-Project `Petty Cash`. A blank remark is not evidence that a spend was non-project; it is
no evidence at all, so this books a claim the data does not support. Chosen over holding such rows
back, so that a confirmed import leaves nothing pending.

**R3 — the statement attachment 403s for most roles (Q23).** The expense's `payment_attachment`
carries the statement's URL, but no second `File` row is created. Frappe authorises a private file
through the document it is attached to, and the statement stays attached to the import batch:

| Doctype | Roles that can read it |
|---|---|
| `Outflow Import Batch` | **3** — Accountant, Accountant Lead, System Manager |
| `Project Expenses` / `Non Project Expenses` | **19** |

So Project Lead, Project Manager, PMO, Procurement, Billing, Design, Sales and Tendering see an
attachment that is visibly present and refuses to open. **Reversing it is one call** —
`expenses._link_statement_file_to_target`, which the Cashfree path already uses — and a test pins
the current behaviour so the reversal has to be deliberate.

**R4 — unapproved spending above the auto-approve limit.** Two rows a fortnight exceed ₹5,000 and
are created `Paid` with no approval anywhere. The `Version` log is the only record that it happened.

### What did NOT change

- **Cashfree is untouched.** Its matcher, its windows, its statuses, its dialog flow. The one shared
  change is three words added to `GENERIC_PROJECT_TOKENS`, measured against all 1,043 staged
  Cashfree rows: **zero** change their project resolution, including the 93 that tier 2 decided and
  every already-`Settled` row. Cashfree remarks name projects in FULL, so they answer at step 1,
  which never consults that list.
- **`Project Payments` still cannot be created by any import.** `settle.create_expense_from_row`
  refuses a non-expense doctype, unchanged.

### Rejected

- **A per-row review step (Q2 option b).** Would have cut R1 to near zero. The owner chose speed:
  this import exists to clear a hundred small rows without a hundred decisions.
- **The one-token project-name guard (Q13).** Built, measured, and dropped: it broke two documented
  behaviours (`Fujitsu` beside `Fujitsu Chennai`; a remark naming two projects) because `ANSR - 2`
  and `Fujitsu` are structurally identical, and no rule can call one a wildcard and the other
  correct. It bought one row. The real fix is renaming such projects in the master, which the
  `project_match` docstring has said since it was written.
- **Deriving the expense type from the sheet's own `Category` column.** Measured unusable: 72 of 115
  rows carry the catch-all `Office Supplies`, and `Bond paper new office agreement` is tagged
  `Food`.

## Open

The owner should revisit **R3** if Project Managers report unopenable attachments, and **R1** if the
monthly correction load in Expenses turns out higher than the ~1–2% measured here.

## Amendment A — a reopened Cashbook line may settle an existing record, by hand only (2026-09-24, #1314, owner)

**Narrows** the Decision's "A **Cashbook** import creates what a wallet already spent; it never settles
an existing record."

The **import** still only creates: the Cashbook job never calls `match_batch`, and the matcher never
runs over a Cashbook line (`sources.NEVER_MATCHED_SOURCES`, unchanged — no suggestion is ever made).
But once a person **unreconciles** a Cashbook line (its created expense is deleted) or **unskips** a
hand-skipped one (ADR-0022 Amendment D), that line is ordinary open work, and a person may do anything
a Cashfree line allows: Create an expense, Link to an existing expense, settle a Project Payment,
Split / Part payment. Every one of those is a person's pick, made in the decision dialog.

- The Create form opens pre-filled from the line's stored plan (`suggested_doctype`,
  `suggested_expense_type`, `resolved_project`), and the expense's Paid by is the statement's `From`,
  as the job writes it.
- The settle reference is the wallet transaction id everywhere, as before (ADR-0020 B9).

## Amendment B — Cashbook spends wait for their invoices, and only the export with bill links is accepted (2026-11-02, owner)

**Status:** Accepted (owner grilling, 2026-11-02). Terms: `GLOSSARY.md` § *Petty-cash wallet (Cashbook)*. Mirrors ADR-0039 decision 8 (card invoices) for the wallet.

**Why.** The wallet provider's newer export, the *Consolidated Company Account Statement*, carries a link to each bill an employee attached. In the sample (2026-04-01 to 2026-10-31), 1,303 of 2,189 spends were linked, with 1,373 files, up to 4 per spend: jpeg 1,331, pdf 35, png 7. It is the old export plus five columns; every Txn Id of an old export reappears in it. The links are signed and all expire 7 days after export. Measuring it also showed three row kinds the import wrongly skips as "moves money between our own balances":

- Collect Payment: 11 rows, a shop-requested payment.
- Refunds: 4 rows, each naming its spend as `REF-<Txn Id>`.
- Wallet Credit: 8 rows, money paid in from outside.

**Decision.**

1. **Only the export with bill links is accepted.** A file without the `Attachments` column is refused with a message naming the export to use. Old batches are untouched; no second parser is kept.
2. **A file whose links have expired, or expire within the hour, is refused**, asking for a fresh export. Chosen over importing without bills, which would leave every bill to attach by hand.
3. **Bills are copied into the system during the import.**
   - The guard: only `https`, only `storage.googleapis.com/prod-payments-private/transaction-attachments/`, no redirects, 10 MB at most, and the bytes must be a JPEG, PNG or PDF.
   - Two or more bills on one spend are merged into one PDF, which becomes the invoice.
   - A download that still fails after three tries leaves the Expense without an invoice. The import summary names it with its reason; it never stops the import.
   - Downloads run outside the line's transaction, because saving a file commits. A bill is attached only after locking the Expense and re-checking that it still has no invoice and no No invoice mark.
4. **Every Cashbook spend without a bill waits** in Vendor Invoice Recon → Pending Invoices Upload → *Cashbook*, Project and Non-Project alike. It waits until an invoice is attached or an Admin or Accountant Lead marks it *No invoice* with a reason (the Credit Card rules). Only Expenses made by this import wait; Expenses made by earlier imports do not.
5. **A bill that arrives later is attached later.** A repeat line that now carries a link attaches its bill to the existing Expense, old or new, when that Expense has no invoice and is not marked No invoice. A file of only repeats is no longer refused when some bring new links.
6. **A Collect Payment is decided by a person.** It is kept open and highlighted on Review, with two choices: Create expense (pre-filled, with its bill copied at import) or Skip by hand.
7. **Refunds and Wallet Credits follow the card rules.** A refund of a whole spend on the same statement skips both lines, each naming the other. Any other refund, and every Wallet Credit, is an open line with the choices an unpaired card credit has.
8. **Lines an earlier import skipped as "own balances" are re-opened** when a new statement carries them and they are a Collect Payment, a refund or a Wallet Credit.

**Considered options.**

- *Import expired files with no bills (they wait).* Rejected: a fresh export is cheap; 1,303 bills by hand is not.
- *First bill as invoice, the rest as extra files.* Rejected: the app screens do not show extra files.
- *Leave old wrong skips alone.* Rejected: real money left the company and was never looked at.

**Open.** The financial year's older Expenses still lack invoices. Decision 5 attaches what each new upload brings; a dedicated catch-up import is future work.
